LFTDO — Rated Construct Evaluation

Each question is answered with a 1–5 rating, written justification referencing specific construct definitions, and recommendations where rating ≤ 3.

Category
Vocabulary & Domain Coverage
BQ-L1Are the core LFTDO constructs clearly and unambiguously defined for the livestock theft domain, or do any definitions introduce terminological overlap or imprecision?

The LFTDO class definitions are clear, domain-specific, and unambiguous at the vocabulary level. Each class definition states what the class represents, what instances belong to it, and how it connects to adjacent classes. The naming conventions (PascalCase classes, camelCase properties) eliminate syntactic ambiguity. The one area of potential overlap is between AbnormalState and TheftIndicator — AbnormalState is a BehaviourState while TheftIndicator is a separate class linked by the indicates property; this distinction is correctly maintained and clearly documented in the definitions.

5
Strongly Supported
BQ-L2Does the LFTDO vocabulary adequately cover livestock theft scenarios including health conditions, environmental factors, and technology components?

Coverage is comprehensive across all three specified domains. HealthCondition (Fever, Injury, Lethargy) covers the physiological disambiguation layer. EnvironmentalCondition (temperature, weather, precipitation) covers the contextual false-alarm reduction layer. The Device class hierarchy (Sensor, UserDevice, CommunicationGateway) covers the technology component layer. One minor gap: there is no explicit PredatorEvent or NaturalDisaster class to represent non-theft causes of abnormal behaviour (referenced in the 18-scenario test suite as Group D false-alarm scenarios). Adding these as subclasses of EnvironmentalCondition would complete the domain coverage.

Recommendation: Add PredatorEvent and WeatherEvent subclasses under EnvironmentalCondition to cover all Group D false-alarm scenarios explicitly in the TBox.

BQ-L3Are all necessary stakeholder roles clearly distinguished? Is UnauthorisedPerson sufficient to model theft intent without conflating with legitimate visitors?

The UnauthorisedPerson class models theft intent correctly as a distinct class with no hasPermission or isAssociatedWithFarm properties — its very definition by exclusion (not a legitimate Participant) is appropriate for representing intruder status. BQ-L4Is the NormalState / AbnormalState distinction sufficiently precise to support automated reasoning? What baseline properties are needed?

The distinction is operationally precise: NormalState is defined by hasBaselineValues and hasDeviationThresholds data properties, while AbnormalState is defined as a statistically significant deviation from these baselines as detected by SWRL rule execution. The transitionStateTo object property (NormalState → AbnormalState) encodes the state machine transition. For full operationalisation, the baseline properties require: (1) species-specific numeric ranges (e.g., sheep grazing speed ≤ 1.5 m/s), (2) duration thresholds (managed by hasDuration via the middleware accumulator), and (3) confidence scoring (hasConfidenceScore on BehaviourState). All three property types are present in the construct vocabulary.

Structural Relationships & Internal Coherence
BQ-L5Does the semantic chain Livestock → exhibitsBehaviour → Behaviour → hasCurrentState → BehaviourState → indicates → TheftIndicator → initiates → TheftEvent form a logically coherent and complete detection pathway?

The detection chain is logically coherent and complete with no gaps between steps. Each link uses a formally defined object property with correct domain and range typing: exhibitsBehaviour (Livestock → Behaviour), hasCurrentState (Behaviour → BehaviourState), indicates (AbnormalState → TheftIndicator), initiates (TheftIndicator → TheftEvent). The contextual inputs (HealthCondition via healthInfluencesBehaviourState, EnvironmentalCondition via environmentInfluencesBehaviourState) branch into BehaviourState from the side, correctly adding contextual disambiguation without breaking the main chain. This is the strongest structural feature of the LFTDO design.

BQ-L6Are the contextual disambiguation relationships (healthInfluencesBehaviourState, environmentInfluencesBehaviourState) sufficient to prevent false theft classifications from health or weather causes?

The two disambiguation object properties provide necessary contextual qualification for BehaviourState classification. The healthInfluencesBehaviourState property allows a HealthCondition (e.g., Fever) to contextualise why an AbnormalState occurred without necessarily triggering TheftIndicator. The environmentInfluencesBehaviourState property serves the same function for EnvironmentalCondition (e.g., extreme heat causing clustering). These are supported by SWRL rules RL_EXTREME_HEAT_CONTEXT and RL_MODERATEHEAT_CONTEXT. One additional property that would strengthen disambiguation: a socialContextInfluencesBehaviourState property to handle community farming events (livestock markets, dipping days) that cause abnormal movement patterns without theft intent — currently absent from the object property set.

Recommendation: Add socialContextInfluencesBehaviourState to handle authorised community-event movement patterns as a third disambiguation branch alongside health and environment.

BQ-L11Are the data properties for SensorData (hasTimeStamp, hasDataType, hasSensorDataValue) and BehaviourState (hasDuration, hasConfidenceScore, hasContext) sufficient for SWRL-based threshold reasoning?

The SensorData properties are sufficient for the primary SWRL rules: hasTimeStamp enables temporal ordering, hasDataType enables type-conditional reasoning, and hasSensorDataValue provides the numeric value for threshold comparison. BQ-L12Does the LFTDO taxonomy demonstrate alignment with or justified departure from established livestock ontology standards (ATOL, EOL, AHOL)?

The LFTDO's domain-specific design (theft detection rather than general livestock management) justifies departure from ATOL (Animal Trait Ontology) and AHOL (Animal Health Ontology), which focus on trait phenotyping and health record management respectively. The LFTDO's Behaviour and BehaviourState classes represent a more dynamic, sensor-driven behavioural model than ATOL's trait-centric vocabulary. The HealthCondition class in LFTDO is a functional disambiguation construct rather than a clinical record system, which distinguishes it from AHOL's clinical focus. A formal alignment declaration (owl:equivalentClass or rdfs:subClassOf links to ATOL/AHOL terms) would strengthen the ontology's reuse credentials, even if full alignment is not pursued.

Recommendation: Add formal owl:equivalentClass or skos:closeMatch alignment declarations to ATOL and AHOL for the Livestock, HealthCondition, and Behaviour classes to enable reuse and federation.

BQ-A1Are the five layers sufficiently distinct in purpose and responsibility? Is there conceptual overlap between the Semantic Layer and Application Layer?

The five layers have clearly delineated responsibilities with no meaningful overlap: Device Layer (data acquisition), Network Layer (transmission), Semantic Layer (transformation and reasoning), Application Layer (presentation), Business Layer (governance). The Semantic Layer and Application Layer are the closest in function — the Semantic Layer produces classified TheftEvents and the Application Layer presents them — but the distinction is clean: the Semantic Layer produces machine-interpretable inferred knowledge (RDF triples, classified instances) while the Application Layer produces human-interpretable outputs (dashboards, alerts, notifications). The Data Mapper as the Semantic Layer's input interface and the API Interface as the Application Layer's output interface make the boundary explicit and non-overlapping.

BQ-A2Is the Semantic Layer's role as intelligence core clearly articulated through its three constructs? Is the data flow from JSON/MQTT → RDF triples → SWRL inference → TheftEvent unambiguous?

The three-construct Semantic Layer structure (Data Mapper → Triple Store & LFTDO → Reasoning Engine) defines a clear sequential pipeline that is explicitly documented. The data flow is unambiguous: JSON/MQTT sensor payloads enter via the Data Mapper, emerge as RDF triples stored in the LFTDO-typed Triple Store, and are then processed by the SWRL Reasoning Engine which fires against the ABox to produce classified TheftEvent individuals. Each step has a named construct responsible for it, and the output of each step is the input of the next. This is the architecture's strongest conceptual articulation.

The "Onto-" prefix claiming ontology centrality is validated by the LFTDO's position as the core of the Semantic Layer, upon which all three other layers depend. The architecture makes this distinction visible through the Data Mapper's role — it creates ABox instances conforming to TBox definitions without modifying the TBox. BQ-A9Are there any critical architectural concerns (data security, system recovery, offline operation, firmware updates) not represented by the five-layer constructs?

Three gaps are identifiable: (1) Offline operation — when LoRaWAN connectivity fails, the Device Layer must buffer sensor readings locally until connectivity is restored. No local storage or buffering construct is defined in the Device Layer. (2) Firmware updates — the Device Layer specifies solar-powered collar tags but does not define an over-the-air (OTA) update mechanism for firmware maintenance in the field. These are implementation-level concerns that would benefit from being named at the construct level to guide development.

Recommendation: Add LocalBuffering construct to Device Layer, OTAUpdateMechanism to Network Layer, and DeviceEncryption to Network Layer constructs to address offline resilience, maintenance, and security gaps.
